# 클러스터 메뉴 설계안 (초안)

같은 인트라넷의 여러 서버가 메인 서버의 작업을 나누어 처리한다. 첫 버전(MVP)을 구현했다: `genomecurator/cluster.py`(메인), `clusterworker.py`(워커), 화면 `/cluster`, 테스트 `tests/test_cluster.py`.

## 원칙
1. **메인이 유일한 원본이다.** DB(SQLite)와 모든 데이터의 원본은 메인에 있다. 서브는 작업용 임시 사본만 갖는다.
2. **서브가 가져간다(pull).** 서브 에이전트가 메인 API에서 작업을 받아 간다. 메인이 서브에 접속해 밀어 넣지 않는다.
3. **입력은 고정된 스냅샷이다.** 작업 명세에 입력 파일 목록과 SHA-256을 적고, 서브는 받은 뒤 해시를 확인한다.
4. **서브는 작업이 끝나 메인이 인수했다고 확인할 때까지만 데이터를 가진다.** 인수 확인(ack) 뒤 작업 폴더를 지운다.
5. **도구는 데이터가 아니다.** BEAST, IQ-TREE 등은 서브마다 설치하고 버전을 고정하며, 등록할 때 알린다.
6. **비공개 서열은 기본적으로 서브로 보내지 않는다.** 작업마다 명시적으로 허용한 경우에만 보내고, 끝나면 폴더를 지운다.
7. **앱은 Pathoplexus에 업로드하지 않는다.** 클러스터에서도 같다.

## 작업 상태
`대기 → 배정 → 입력 전송 → 실행 → 결과 전송 → 인수 확인 → 정리`
- 실패: 서브가 오류를 보고하거나 heartbeat가 끊기면 `대기`로 돌아가 다른 서브가 받는다(시도 횟수 상한, 상한 후 `오류`).
- 입력이 고정 스냅샷이라 재시도 결과는 같다. 결과는 작업 번호와 해시로 받아 중복 수신을 거른다.
- 메인이 죽으면: 실행 중인 작업은 서브가 끝까지 돌린다. 결과와 보고는 서브에 남겨 두었다가 메인이 돌아오면 보낸다. 새 작업 배정은 멈춘다.

## 서브 에이전트
- 등록: 이름, CPU 코어, 메모리, 설치된 도구와 버전, 작업 폴더의 여유 공간. 서브마다 개별 키로 인증하고 폐기할 수 있다. 키는 사용자가 직접 만들어 넣는다.
- heartbeat: 일정 간격. 일정 시간 끊기면 메인은 그 서브의 작업을 되돌린다.
- 작업 수령 조건: 필요한 도구와 버전이 있고, 코어와 메모리가 맞고, 비공개 허용 여부가 맞을 때만 가져간다.
- 서브는 DB에 직접 쓰지 않는다. 모든 보고는 메인 API를 거친다(SQLite 단일 기록자 유지).

## 메인 API (초안)
| 호출 | 용도 |
|---|---|
| POST /cluster/register | 서브 등록과 능력 보고 |
| POST /cluster/heartbeat | 생존 신호, 진행 상황 |
| POST /cluster/claim | 맞는 작업 하나 받기 |
| GET /cluster/jobs/{id}/inputs/{sha} | 입력 파일 내려받기(해시로 확인) |
| PUT /cluster/jobs/{id}/outputs/{sha} | 결과 올리기 |
| POST /cluster/jobs/{id}/done / fail | 완료, 실패 보고 |
| POST /cluster/jobs/{id}/ack | (메인→서브 응답) 인수 확인, 서브가 폴더를 지움 |

## 재현성
작업마다 `repro` 매니페스트를 붙인다(입력 해시, 서브 이름, 도구 버전, 매개변수, 결과 해시). 어느 서브에서 돌렸는지 기록되고 같은 입력이면 같은 결과임을 대조할 수 있다.

## 화면(클러스터 메뉴)
- 서브 목록: 상태(온라인/끊김), 도구와 버전, 현재 작업, 마지막 heartbeat, 여유 공간.
- 작업 큐: 상태, 배정된 서브, 진행 시간, 시도 횟수, 재시도/취소.
- 작업 만들 때: "서브에서 실행" 선택, 비공개 서열 허용 체크(기본 꺼짐), 필요한 도구.

## 나중에 (지금은 하지 않음)
- 같은 입력 반복 실행(시드)을 위한 서브의 해시 캐시.
- 메인 복구: SQLite 복제(NAS 등)와 사람이 승격하는 대기 메인. 자동 승격은 필요가 확인된 뒤에.
- 한 분석을 잘게 쪼개 나누기(처음에는 BEAST 한 번, IQ-TREE 한 번 같은 기존 실행 단위를 한 작업으로).

## 첫 구현 범위 (MVP)
서브 등록과 heartbeat, 작업 수령, BEAST 작업 하나를 서브에서 실행하고 결과를 해시로 확인해 인수하는 흐름, 서브 끊김 시 재배정, 클러스터 화면의 서브 목록과 작업 큐.

## 사용법 (구현된 첫 버전)
1. 메인을 다른 서버가 접속할 수 있게 띄운다: `genomecurator serve --host 0.0.0.0`. 이렇게 띄워도 **다른 컴퓨터는 워커 API(`/api/cluster/w/…`, 워커 키 필요)만** 쓸 수 있고, 화면과 나머지 API는 403이다(로그인이 없는 앱이라 비공개 유전체를 보호하려는 것). 메인이 있는 컴퓨터에서는 전부 쓸 수 있다. 신뢰하는 내부망에서 앱 전체를 공유하려면 `GC_ALLOW_REMOTE_UI=1`. 같은 인트라넷 안에서만 쓰고 바깥에 열지 않는다.
2. **시스템 > 클러스터**에서 워커를 추가한다. 키는 그때 한 번만 보인다.
3. 워커 서버에서 (a) 이 프로그램의 **클러스터 화면 > "이 서버를 서브서버로 사용"**에 메인 주소와 키를 넣고 **활성화**를 누른다. 서버가 메인에 접속해 작업을 가져가며, 프로그램을 다시 켜도 유지된다(키는 데이터 폴더의 `cluster/worker.json`에 소유자만 읽게 저장, DB·백업에는 없음). 또는 (b) 명령줄에서: `genomecurator worker --main http://메인:8000 --key <키> --workdir gc-worker` (BEAST가 설치되어 있어야 한다. 위치는 `--beast`로 지정할 수 있다).
4. 준비된 BEAST 폴더를 작업으로 넣는다(화면 또는 `genomecurator cluster-submit <폴더>`). 결과는 같은 폴더에 들어오고 `cluster_job.json`에 어느 워커가 돌렸는지와 파일 해시가 남는다.

## 참여 요청과 승인
1. 서브서버 화면에서 **분석 환경 점검**(BEAST가 실행되는지, BEAGLE 라이브러리, 작업 폴더 여유 10GB 이상: `GC_WORKER_MIN_FREE_GB`)이 모두 통과해야 **참여 요청** 버튼이 켜진다. 메인도 점검이 실패한 요청은 받지 않는다.
2. 요청(서버 이름, IP, 점검 결과, CPU·메모리·디스크, 도구·OS·앱 버전)이 메인 클러스터 화면의 **승인 대기**에 나타난다. 관리자가 승인(비공개 허용 여부 포함)하거나 거절한다. 24시간 안에 결정하지 않은 요청은 지워진다.
3. 승인되면 서브서버가 확인하러 올 때 메인이 그 서버 전용 키를 만들어 **한 번만** 넘긴다(키는 메인 DB에 해시로만 남음). 서브서버는 키를 저장하고 스스로 작업을 받기 시작한다. 요청을 증명하는 비밀값도 서브서버가 만들고 메인은 해시만 가진다.
4. 승인 뒤에도 서브서버는 10분마다 환경을 다시 점검하고, 깨지면 작업을 받지 않고 메인에 "이상"으로 보고한다. 메인에서 **환경 다시 점검**을 누르면 다음 연락 때 바로 점검한다.

## 진행 상황, 정지, 유예
- 메인의 서브서버 표와 작업 표, 서브서버 화면 모두 진행률(%), 수행 시간, 남은 시간 추정, 완료 예상 시각을 보여 준다. 서브서버 화면에는 최근 작업 10개의 결과와 걸린 시간도 나온다.
- **정지**(서브서버 화면): 실행 중인 작업과 그 자식 프로세스(BEAST의 Java)를 끝내고 메인에 바로 돌려준다. 메인은 시도 횟수에 넣지 않고 다시 나눈다. **재개**할 때까지 새 작업을 받지 않으며, 다시 켜도 정지 상태가 유지된다.
- **유예**: heartbeat가 90초(`GC_CLUSTER_STALE`) 넘게 없으면 "응답 없음"과 남은 유예 시간을 표시한다. 10분(`GC_CLUSTER_LEASE`, 초)이 지나도 없으면 그 서브서버에서는 실패한 것으로 보고 대기열로 돌려 다른 서브서버에 나눈다(시도 횟수에 포함). 늦게 돌아온 서브서버의 결과는 받지 않는다.

## 웹 터미널
- 서브서버 화면의 **웹 터미널 허용**을 켜면(기본 꺼짐) 메인 클러스터 화면의 그 서브서버 줄에 **터미널** 버튼이 생긴다. 누르면 새 창에서 서브서버의 셸이 열린다(PTY라 top, vim, tail -f 가능). Linux와 macOS 서브서버만.
- 인증: 메인이 1분짜리 일회용 토큰을 만들어 그 서브서버 키의 SHA-256으로 서명하고, 서브서버가 자기 키로 확인한다. 메인은 키의 해시만, 서브서버는 키만 가진다. 토큰은 웹소켓 첫 메시지로 보내 주소나 로그에 남지 않는다. 토큰은 메인이 있는 컴퓨터에서만 만들 수 있다.
- 셸은 서브서버 프로그램을 띄운 사용자 권한으로 홈 폴더에서 시작한다. 창을 닫거나 연결이 끊기면 셸과 그 자식 프로세스가 끝난다.
- 접속 시작·종료(누가, 언제, 얼마나)는 양쪽 서버의 감사 로그에 남는다. 입력 내용은 기록하지 않는다. 서브서버 화면에 지금 접속 중인 세션이 보인다.
- 필요: `pip install "genomecurator[cluster]"`(websockets). 터미널 화면(xterm.js)은 앱에 포함되어 인터넷이 없어도 된다.
- 주의: 직접 연결한 신뢰하는 망을 전제로 한다. `--host 0.0.0.0` 대신 직결선 쪽 주소(예: `--host 10.0.0.2`)로 띄우면 다른 랜카드로는 열리지 않는다.

## Netdata 연동 (선택)
서버에 Netdata 에이전트(GPL-3.0, 포트 19999)가 돌고 있으면 이 앱이 그 API를 읽는다. Netdata를 설치하거나 포함하지 않으며(설치는 root 권한이 필요해 사용자가 한다), 없으면 지금처럼 현재 값만 보여 준다.
1. **감지와 링크**: 서브서버가 자기 Netdata를 찾아 메인에 알린다(10분마다 다시 확인). 메인의 서브서버 줄과 서브서버 화면에 "Netdata ↗" 대시보드 링크가 생기고, Netdata Cloud에 연결되어 있으면 경고를 띄운다.
2. **기록 그래프**: CPU(%), 메모리(%), 디스크 읽기·쓰기(MB/s), 네트워크 받기·보내기(Mbit/s)를 1시간·6시간·24시간·7일로 보여 주고, 그 서버에서 클러스터 작업이 돈 구간을 초록 띠로 겹친다. 메인은 서브서버의 Netdata를 직접 읽고, 닿지 않으면 메인 Netdata에 스트리밍된 기록을 호스트 이름으로 읽는다.
3. **스트리밍 안내**: 메인 클러스터 화면의 "Netdata 스트리밍"에 메인(부모)과 서브서버(자식)의 `stream.conf` 내용을 만들어 보여 준다. API 키는 한 번 만들어 보관하고, 메인 주소는 서브서버로 가는 연결에서 찾으며, 받는 쪽은 그 대역(예: `10.0.0.*`)만 허용한다. 어느 서브서버가 보내고 있는지도 표시한다. 클라우드 없이 메인 한곳에 모든 서버의 기록이 모인다.
- 권장: 서브서버의 Netdata Cloud는 끈다(`/var/lib/netdata/cloud.d`를 옮기고 다시 시작). 안정(stable) 버전을 쓴다. 대시보드 화면(v2)은 Netdata의 별도 라이선스이므로 이 앱은 화면을 포함하지 않고 API만 읽는다.

## 서브서버 화면 (`/cluster/sub`)
- 서브서버로 쓸 서버의 주소(`http://그 서버:8000`)로 접속하면 이 화면으로 온다. 같은 **사설 네트워크**(10.x, 172.16-31.x, 192.168.x 등)의 컴퓨터에서만 열리고, 공인 IP나 다른 화면은 403이다(`GC_SUB_PAGE_LAN=0`이면 이 화면도 이 서버에서만).
- **참여 요청/비활성화/정지/재개**: 위의 흐름. 상태(승인 대기, 활성화됨, 작업 실행 중, 정지됨, 환경 이상, 메인에 연결할 수 없음)가 3초마다 갱신된다. 메인에서 직접 받은 키로 시작하는 방법도 남아 있다(명령줄 워커와 같은 방식).
- **자원 사용**: CPU, 메모리, 데이터 폴더의 디스크, 부하. 워커가 메인에 보고하므로 메인의 클러스터 화면 워커 표에도 보인다.
- **설치하기**: BEAST 10과 BEAGLE이 없으면 conda 환경 `gc-beast`를 만든다(mamba/conda와 인터넷 필요). 진행 로그가 화면에 나온다.
- 이 화면에서는 누구나 활성화, 설치를 할 수 있으므로 신뢰하는 네트워크에서만 쓴다. 워커 키는 메인의 클러스터 화면(메인이 있는 컴퓨터)에서만 만들 수 있다.

## 알려진 한계 (첫 버전)
- 작업 종류는 BEAST 하나, 워커당 한 번에 한 작업. 입력 캐시와 대기 메인 복구(SQLite 복제)는 아직 없다.
- 워커와 메인의 통신은 암호화하지 않는다(HTTP). 키는 요청 머리글로 오간다. 신뢰하는 내부망에서만 쓴다.
