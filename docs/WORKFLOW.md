# 전체 워크플로 / How the whole thing works

## 1. 데이터가 들어오는 길 (사용자 관점)

```
 바이러스 등록 ──► 지금 확인 ──► changeset(변경 사항 묶음) ──► 검토 ──► 적용
 (이름은 NCBI에서     │          아직 아무것도 안 바뀜        │        │
  바이러스인지 확인)   │                                       │        ├─ 표(DB)와 FASTA에 반영 (실패하면 전부 되돌림)
                      │                                       │        └─ 값마다 출처(provenance) 기록
                      ▼                                       ▼
        NCBI(accession 집합을 정함)             승인 / 거절 / 보류
        Pathoplexus · BV-BRC(보강)              소스끼리 다른 값은 직접 고르기(추천·신뢰도, 일괄 선택)
        Nextclade(QC 후, clade/lineage가 4번째 소스)
```

1. **등록**: 바이러스 이름 → NCBI에서 분류군 확인(바이러스가 아니면 거절).
2. **지금 확인**(수동 또는 매일 자동): 세 소스를 조회해 내 데이터와 비교하고, 달라진 항목만 *changeset*으로 쌓습니다. 소스가 하나라도 응답하지 않으면 값이 비워질 수 있으므로 확인 자체를 중단합니다.
3. **정합성**: 같은 accession을 소스끼리 필드별로 비교해 일치 / 표기 차이 / 진짜 불일치로 나눕니다. 애매하면 **서열 검증**(헤더를 뺀 본문 SHA-256, dry-run 먼저).
4. **검토**: 승인·거절·보류. 불일치 항목은 소스별 값과 추천을 보고 고르거나(여러 건은 체크박스·드래그·Shift+클릭 후 *선택 항목에 추천 적용*), Auto-pick(전체).
5. **적용**: 점검(디스크·링크·샘플 서열) 후 반영. 거절한 것은 같은 내용이면 다시 올라오지 않습니다.
6. **QC**(서열이 있는 유전체): 서열 통계는 모두, Nextclade는 데이터셋이 있는 바이러스만. 경고만 하며, Nextclade가 부른 clade/lineage는 소스와 다르면 *검토 화면*으로 올라옵니다(자동으로 덮어쓰지 않음).
7. **감시**: 매일 새벽 스키마 점검으로 소스의 응답 구조가 바뀌었는지 봅니다. 헤더의 신호등(NCBI — Pathoplexus — BV-BRC)과 스키마 탭에 결과가 보입니다.
8. **비공개 유전체**: 공개되지 않은 로컬 유전체는 *비공개* 탭(CLI `private-check`/`private-import`)으로 공개 데이터와 분리된 저장소에 가져오고(dry-run 먼저), QC를 돌립니다. 내보내기에서 *비공개 포함*을 켜면 별도 파일로만 나갑니다.
9. **데이터셋**: 분석에 쓸 유전체를 규칙으로 골라(예: clade Ib만) 이름을 붙여 저장하고, 내보낼 때 그 시점의 멤버가 확정되어 manifest에 규칙과 멤버 해시가 남습니다.
10. **Nextstrain 분석**: *Nextstrain* 탭에서 데이터셋을 워크플로 체크아웃에 내보내 설정 overlay와 함께 `nextstrain build`로 돌립니다(서버 작업). 분석마다 멤버 해시·규칙·설정·워크플로 커밋·도구 버전과 결과가 **보관**되고, 오늘의 데이터셋과 비교해 어느 결과가 현재 데이터와 맞는지 보며, 로컬 Auspice로 골라 엽니다.
11. **다른 프로그램에 넘기기**: *내보내기* 탭·CLI(`export`)·내부 API가 같은 id·순서의 `metadata.tsv` + `sequences.fasta` + `manifest.json`을 만듭니다(Nextstrain mpox 워크플로 형식 지원: `--nextstrain-dir`로 체크아웃에 바로 써 주며, 워크플로의 기본값 config 뒤에 overlay를 붙여 로컬 입력으로 돌립니다). 그 밖의 내보내기: 유전체 표 TSV, Superset 분석(읽기 전용), GitHub Pages용 정적 페이지(배포하기), 백업(zip).

## 2. 서버 안에서 (작업과 기록)

- 오래 걸리는 일(추가·조회·확인·적용·FASTA·검증·QC·스키마·배포·자동 실행)은 모두 서버 **작업**입니다. 상태·진행률·로그·오류가 DB(`job`)에 남아 다른 메뉴로 가거나 서버를 재시작해도 **작업 탭**에서 볼 수 있고, 재시작 때 진행 중이던 것은 *중단*으로 표시됩니다.
- 스케줄러(APScheduler)가 자동 확인과 매일 스키마 점검을 돌며, 이들도 작업으로 기록됩니다.
- 로그: `data/logs/genomecurator.log`(회전, 작업·바이러스 맥락 포함). 사용자 작업 기록은 `audit_log`(이력 탭).

## 3. 개발·배포 워크플로 (GitHub)

| 단계 | 어디서 | 내용 |
|---|---|---|
| 개발 | 로컬(conda `genomecurator`) | 코드 수정 → `python -m pytest -q`(테스트 통과를 커밋 조건으로) |
| 기록 | `CHANGELOG.md`·`CHANGELOG.ko.md` | `[Unreleased]`에 변경마다 추가(Keep a Changelog + SemVer) |
| 커밋·push | 터미널(토큰은 사용자가 입력) | `main`에 push. 이미 push한 이력은 다시 쓰지 않음 |
| CI (`ci.yml`) | GitHub Actions | Windows·macOS(ARM)·Linux × Python 3.10/3.12 테스트, `environment.yml`이 실제로 빌드되는지(x86 + ARM 리눅스) 확인 |
| 이미지 (`docker.yml`) | GitHub Actions | amd64·arm64 이미지를 매번 빌드해 확인, **`v*` 태그일 때만** GHCR에 게시 |
| 릴리스 | `docs/RELEASING.md` | CHANGELOG 정리 → `__version__` → 테스트 → 릴리스 커밋 → 주석 태그 `vX.Y.Z` → push(커밋+태그) |
| 공개 페이지 | 앱의 *배포하기* | 미리보기로 바이러스·유전체 수를 보여 주고 확인을 받은 뒤 `docs/index.html`만 커밋·push → GitHub Pages |

## 4. 지키는 원칙

- **데이터 정합성 최우선**, 문제는 **경고**로 알리고 막지 않습니다(예외: 소스 응답 실패 시 값 유실을 막으려 확인 중단).
- 승인 전에는 아무것도 바뀌지 않고, 자동 도구(추천, Nextclade)는 **제안**만 합니다. 고르는 건 사람입니다.
- 비밀값(토큰·비밀번호)은 채팅·저장소에 두지 않습니다(`superset/home/`, `data/`는 git 제외).
- 바이러스 전용(세균은 별도 프로젝트).
