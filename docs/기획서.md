# GenomeCurator 기획서

작성일 2026-10-16 · 저장소 https://github.com/CHOICHI-HWAN/GenomeCurator

## 1. 배경과 목적

바이러스 유전체 연구에서는 NCBI Virus, Pathoplexus, BV-BRC 등 여러 공개 DB의 데이터를 함께 봐야 한다. 새 서열이 올라오거나 기존 레코드의 메타데이터와 GenBank accession 버전이 바뀌어도 이를 한눈에 확인하기 어렵다.

**GenomeCurator**는 관심 바이러스를 등록해 두면 외부 DB를 주기적으로 확인하고, **무엇이 바뀌었는지를 사람이 검토·승인한 뒤에만** 로컬 데이터에 반영하는 로컬 웹 도구다. 로컬 데이터는 BV-BRC 형식으로 정리해 이후 분석에 바로 쓸 수 있게 한다.

## 2. 핵심 요구사항 (확정)

| # | 요구 | 반영 방식 |
|---|---|---|
| 1 | NCBI Virus에서 원하는 바이러스 유전체 수집 | NCBI Datasets v2 Virus API (메타데이터 + 서열) |
| 2 | 주기적으로 새 데이터 확인 | APScheduler (기본 24시간, 환경변수로 변경) + "지금 확인" 버튼 |
| 3 | 업데이트 전 사용자에게 알리고 허락받기 | 변경은 changeset으로만 쌓고, 큐레이션 화면에서 승인해야 반영 |
| 4 | 반영 전 dry-run으로 동작 가능 여부 확인 | 다운로드 엔드포인트, 디스크 여유, 샘플 서열 길이·md5 검증. 통과해야 READY |
| 5 | 내부 포맷은 BV-BRC 형식 | `genome`, `genome_sequence` 테이블과 BV-BRC 컬럼명 사용 |
| 6 | 소스 우선순위 Pathoplexus > NCBI Virus > BV-BRC | 필드별로 값이 충돌하면 우선순위 높은 값 채택, 출처를 필드별로 기록 |
| 7 | 변경 기준: 메타데이터 변경, GenBank `.version` 증가 | 둘 다 changed로 판정 (신규 new, 사라짐 removed 포함) |
| 8 | 바이러스는 계속 추가, 첫 대상은 Henipavirus nipahense | Watchlist 구조 (이름 + NCBI taxon) |
| 9 | 로컬 PC에서 실행, 코드는 GitHub 보관 | 설치형 서버 없이 `pip install -e .` 후 실행 |

## 3. 전체 흐름

```
Watchlist → 확인(check) → Dry-run → Changeset(보류) → 큐레이션 화면 → 승인 → Apply → 로컬 DB·FASTA
(바이러스)  3개 소스 병합    링크·디스크·샘플     READY/BLOCKED    필터·정렬·diff    건별/일괄   파일 교체+DB 트랜잭션
```

**원칙: 승인 전에는 로컬 데이터를 절대 바꾸지 않는다.** Apply는 파일을 백업한 뒤 교체하고 DB는 한 트랜잭션으로 반영하며, 실패하면 파일을 되돌린다. 거절한 항목은 같은 내용이면 다음 확인에서 다시 올라오지 않는다.

## 4. 데이터 소스

| 소스 | 역할 | 방식 | 검증 결과 (실호출) |
|---|---|---|---|
| NCBI Virus | accession 집합과 서열의 기준 | Datasets v2 `dataset_report`, `genome/download` | 동작 확인. HEAD 요청은 405라 dry-run은 샘플 다운로드로 대체 |
| BV-BRC | 메타데이터 보강, 컬럼명 기준 | Data API `genome/?eq(taxon_lineage_ids,X)` | 동작 확인 |
| Pathoplexus | 가장 이른 메타데이터 | LAPIS `sample/details` | organism 목록 API가 없어 확인된 14개 slug를 NCBI taxon으로 자동 탐색. Monkeypox ↔ `mpox` 연결 확인 |

- join 키는 INSDC accession(버전 제외). Pathoplexus에 해당 바이러스가 없으면(예: Nipah) 오류 없이 건너뛴다.
- 값 충돌 시 필드별 채택 소스를 `field_provenance`에 저장하고, 화면에서 배지(`pathoplexus`/`ncbi`/`bvbrc`)로 보여 준다.

## 5. 데이터 모델 (BV-BRC 형식)

- `genome`: genome_id(`taxon_id.순번`), genome_name, genome_status, genome_length, genbank/refseq accession, strain, host_name, isolation_country, geographic_location, collection_date, genotype, subtype, taxon lineage 등
- `genome_sequence`: accession, version, length, gc_content, md5, 파일 경로
- `source_record`: 소스별 원본 응답 보관 (병합과 diff의 근거)
- `field_provenance`: 필드별 채택 소스
- `genome_version`: 변경 전 스냅샷 이력
- `changeset` / `changeset_item`: 변경 묶음과 항목별 결정(pending/approved/rejected/hold/applied)
- `audit_log`: 작업 이력
- 디스크: `data/genomes/<바이러스>/<genome_id>.fna`, `data/staging/`, `data/snapshots/`

## 6. 화면 구성 (BV-BRC Taxon View 스타일)

| 화면 | 내용 |
|---|---|
| **큐레이션 (홈)** | Watchlist 관리, "지금 확인", changeset 목록과 승인 대기 배지 |
| **Changeset** | 신규/변경/삭제 요약, dry-run 결과, BV-BRC 형식 표에서 필터·정렬 후 승인·거절·보류·적용. 변경된 칸은 노란색으로 이전 값과 함께 표시 |
| **Genomes** | 계통 경로(breadcrumb), 탭, 도구줄(Download/Keywords/Select Columns/Filters), 촘촘한 표, 왼쪽 필터 패널(건수 실시간 갱신), 오른쪽 상세 패널(필드별 출처 배지), 선택 항목 TSV/FASTA 다운로드 |
| **Overview (대시보드)** | 요약 카드, 월별 신규 등록, 수집 연도, 국가별(클릭 시 필터), 숙주별, 서열 길이 분포, 메타데이터 완성도 |
| **History** | 확인·승인·적용 이력 |
| 공통 | 장시간 작업(확인, 적용)은 화면 오른쪽 아래 진행 표시줄(토스트)로 진행률 표시 |

## 7. 기술 스택

Python 3.10+ · FastAPI · SQLite(WAL) · APScheduler · Jinja2 · 순수 JS(표) · Chart.js(대시보드, CDN)

- 서버 설치, 로그인, 외부 AI API를 쓰지 않는다. 단일 사용자 로컬 실행을 가정한다 (인증 없음).
- Apache Superset 임베드는 검토 후 보류했다. Windows 설치 부담과 임베드 설정 복잡도에 비해 필요한 차트가 단순하기 때문이다. 데이터가 SQLite라서 나중에 읽기 전용으로 별도 연결할 수 있다.

## 9. 위험과 대응

| 위험 | 대응 |
|---|---|
| 외부 API 스키마·정책 변경 | 소스 어댑터를 분리하고 원본 응답을 `source_record`에 보관 |
| 대용량 바이러스(수만 건) 성능 | 표는 클라이언트 페이징, 향후 서버 측 페이징·가상 스크롤 |
| NCBI 호출 제한 | API key 선택 입력, 호출 간격 자동 조절 |
| 소스 간 필드 표기 차이 | 병합 시 필드별 출처 기록, 정규화 단계를 추후 추가 |
| 임시 작업 환경 | 모든 코드와 문서를 GitHub에 보관, `docs/STATUS.md`로 이어서 작업 |
