# 구조 점검: 파이프라인의 결합도와 Snakemake (2026-10-20)

코드의 모듈 의존 관계를 실제로 계산하고(`genomecurator/*.py`의 import), 분석 모듈의 실행 방식을 읽어서 정리했습니다. Snakemake는 **시제품을 만들어 보지 않고** 구조만 보고 검토한 것이라, 아래 "권고"는 가정이 들어 있습니다.

## 지금 구조에서 느슨한 부분 (좋은 점)
- **도구가 별개 프로그램입니다.** Nextstrain, Squirrel, snippy, lofreq는 각자의 conda 환경(`gc-nextstrain`, `gc-squirrel`, `gc-snippy`, `gc-lofreq`)에서 따로 실행되고, 서로 **파일**(FASTA → 정렬 → VCF/TSV)로만 주고받습니다. 앱 안에서 그 도구들의 라이브러리를 import 하지 않습니다.
- **기록이 한 곳입니다.** 모든 분석 실행은 `analysis_run` 표에 같은 모양(멤버 해시, 내용 해시, 설정, 도구 버전, 로그, 실행 폴더)으로 남고, 같은 입력·설정이면 재사용됩니다.
- **돌려 쓰는 기반 모듈**(`log`, `config`, `db`)이 가장 많이 import 되고(25·23·21곳), 이들은 다른 모듈에 의존하지 않습니다. 의존이 아래로만 흐릅니다.

## 단단하게 묶인 부분 (문제)
1. **`mutprofile`이 허브입니다.** 11개 모듈에 의존하고(`squirrel`, `nextstrain`, `export`, `datasets`, `lineages`, `aligned`, `sources`, `pathoplexus` …) 10개 모듈이 `mutprofile`을 import 합니다. 변이 프로파일 실행이 곧 "Squirrel 정렬 → 변이 호출 → 계통 정의 연결"의 순서를 코드 안에 박아 두고 있습니다.
2. **순환 의존이 5쌍 있습니다**: `mutprofile↔lineages`, `mutprofile↔aligned`, `lineages↔aligned`, `datasets↔export`, `curate↔resolve`. 함수 안에서 늦게 import 하는 식으로 피해 왔지만, 바꿀 때 어디가 깨지는지 한눈에 보이지 않습니다.
3. **결과 화면 모듈이 서로를 호출합니다**: `heatmap→insight`, `novel→outbreak→insight`, `cooccur→novel`. 한 계산을 고치면 다른 화면이 바뀝니다. (같은 `mutations.tsv`를 읽는다는 점은 안정적입니다.)
4. **단계 순서가 파이썬 제어 흐름에 숨어 있습니다.** 실제 흐름은 `멤버 → FASTA 내보내기 → Squirrel 정렬 → mutprofile / variantcall / 합의 마스크 → 결과 화면`인데, 이 그래프가 어디에도 선언되어 있지 않고 `mutprofile.run()`이 `squirrel.align_run()`을 부르는 식으로 암묵적입니다.
5. **같은 실행 틀이 4번 복사되어 있습니다.** (`nextstrain`, `squirrel`, `mutprofile`, `variantcall`) 환경 찾기 → 실행 폴더 → `analysis_run` 행 → 로그·진행률 → 재사용 판단. 하나를 고치면 나머지에 같은 수정이 필요합니다.
6. **원숭이두창 가정이 코드에 박혀 있습니다**: 참조 서열 고르기, clade→Squirrel 참조 매핑, 계통 정의. 다른 바이러스를 추가하려면 여러 모듈을 고쳐야 합니다(이 때문에 화면에 구현 상태 뱃지를 붙였습니다).
7. **중간에 끊기면 처음부터입니다.** 예: `variantcall`은 1,142개 유전체를 한 번에 돌리고 끝에 파일을 쓰므로, 99%에서 멈추면 전부 다시 해야 합니다.

## Snakemake로 관리하면 어떨까
**잘 맞는 부분**: 위 4번의 그래프가 정확히 Snakemake가 다루는 모양입니다(파일이 입력·출력인 단계들). 얻는 것은 ① 단계 의존이 `Snakefile`에 선언됨, ② **바뀐 것만 다시 실행**(내용 기준) · 중간에 끊겨도 이어서 실행, ③ 유전체별 작업(snippy 1,142개)을 병렬·재시도로 처리, ④ 규칙마다 `conda:` 환경 선언(지금의 `gc-*` 환경 관리를 대체), ⑤ 로그·벤치마크·재현 가능한 보고. 게다가 Nextstrain mpox 워크플로가 이미 Snakemake라서 같은 방식으로 합칠 수 있습니다.

**맞지 않는 부분**: 수집·큐레이션·승인·DB(트랜잭션, 사람의 승인 단계)와 웹 화면은 파일 파이프라인이 아니므로 앱에 남겨야 합니다. 결과 화면의 계산(insight 등)은 요청 시 즉시 계산하는 것이라 대상이 아닙니다.

**위험·비용**
- 진행률을 화면에 보여주는 방식을 새로 만들어야 합니다(지금은 로그를 읽어 진행률 계산). Snakemake의 로그/상태를 파싱하는 코드가 필요합니다.
- `analysis_run` 기록과 Snakemake의 자체 메타데이터(`.snakemake/`)를 이어 주는 코드가 필요합니다. 같은 사실이 두 곳에 있게 되면 어긋날 수 있습니다.
- 규칙마다 conda 환경을 만들면 처음 실행이 느리고 오프라인에서 못 만듭니다. 지금 방식(미리 만든 이름 있는 환경)을 유지하고 규칙에서 그 이름을 쓰는 절충이 가능합니다.
- **Windows**: Snakemake는 Linux/macOS 중심으로 알고 있고(Windows는 WSL), 이 프로젝트는 Windows CI가 있습니다. 다만 생물정보 도구(Nextstrain·Squirrel·snippy)가 이미 Linux/macOS 전제라, 분석 파이프라인만 Snakemake로 옮기는 것은 새로운 제약이 아닙니다. 수집·큐레이션 쪽은 그대로 Windows에서 돕니다. (이 부분은 확인하지 못했고 알고 있는 바에 근거한 것입니다.)
- 배울 것과 의존성이 늘고, 디버깅이 한 단계 더 멀어집니다.

## 권고 (단계적, 먼저 싼 것부터)
1. **지금 하기 쉬운 정리**: 위 5번의 실행 틀을 한 모듈(`runs.py`)로 모으고, 순환 의존 5쌍을 끊습니다(공통 함수를 아래 모듈로 내림). 동작은 그대로이고 테스트가 있어 안전합니다.
2. **시험 삼아 하나만 Snakemake로**: 새 **변이 검증 파이프라인**(Squirrel 정렬 → 유전체별 snippy → lofreq → 일치도 → 합의 마스크 후보)을 `Snakefile` 하나로 만들어 앱이 `nextstrain build`를 부르듯 실행합니다. 유전체별 병렬 작업이고 중간 재개가 필요해서(위 7번) 가장 이득이 큰 곳이며, 실패해도 기존 분석에 영향이 없습니다.
3. **시험 결과를 보고 결정**: 진행률 연동과 `analysis_run` 연결이 깔끔하게 되면 `mutprofile`의 정렬·호출 단계도 옮깁니다. 아니면 1번의 정리만으로 두고 멈춥니다.

한 번에 전부 옮기는 것은 권하지 않습니다. 지금 동작하는 분석이 많고(테스트 105건), 옮기는 이득이 가장 큰 곳과 위험이 가장 작은 곳이 겹치는 것이 2번입니다.
