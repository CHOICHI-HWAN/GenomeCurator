They may be wrong, incomplete or change without notice. Do not cite, reuse or build on them until they have been verified and published by the authors.

and versions follow [Semantic Versioning](https://semver.org/) (while the major version is 0, a minor bump may change behaviour;

## [Unreleased]

### Added
- **Cluster (first version)** (opening a server's address from the same private network shows a sub-server page: activate/deactivate, one-button BEAST install, CPU/memory/disk use and job progress; the main server shows the same use per worker): other servers on the same network can take BEAST jobs from the main server (menu *System > Cluster*, `genomecurator worker`, `genomecurator cluster-submit`). The main server stays the only source of truth: a worker pulls a job, copies its input files (SHA-256 checked), runs the fixed command, and sends the result files back; the main server verifies every hash, installs the files in the job's folder and only then lets the worker delete its copy. A worker that goes silent loses its job to the queue (attempt limit), a running job survives a restart of the main server (results wait on the worker), private genomes go only to workers set up to accept them, and each worker has its own key (stored as a hash). Design: [docs/CLUSTER_DESIGN.ko.md](docs/CLUSTER_DESIGN.ko.md).
- **Reproducible tree figures.** `genomecurator.treefigure.render()` draws a publication-style figure of a BEAST summary tree (calendar axis, clade of interest last, side clades collapsed into triangles with their composition, lineage chips, posterior marks, credible-interval bars) from one call, and `genomecurator.repro.manifest()` writes `<figure>.manifest.json` next to it: SHA-256 of every input, parameters, program / library / BEAST / TreeAnnotator versions and the SHA-256 of the files written (`repro.verify` checks them). The same inputs give a byte-identical SVG. A private genome in the tree must be given an alias, otherwise no figure is made. matplotlib is optional (`genomecurator[figures]`). See docs/REPRODUCIBILITY.md.
- **BEAST: the SkyGrid tree prior** (`tree_prior: skygrid`, with `skygrid_points`, one grid cell per month by default, reaching one year beyond the sampled time span). A flexible, time-varying population size instead of one growth rate, so a date estimate can be checked against the exponential-growth and constant-size priors. Not available for the marginal-likelihood (BETS / GSS) comparison, which still compares strict / relaxed x constant / exponential.
- **BEAST: rate variation among sites can be chosen** (`site_rates` in the BEAST settings: `gamma` (default, four categories), `inv` (a proportion of invariant sites) or `gamma_inv`), so that the substitution model suggested by a model-selection tool such as ModelFinder can be used and its effect on the dates checked. Without the option nothing changes.
- **BETS estimations can have a name** (`name` in the BETS settings): each keeps its own folder `bets/<name>/`, so two estimations (for example a strict and a relaxed clock) can run at the same time. Before, they shared `bets/` and overwrote each other's analyses when started together.
- **PearTree as the tree viewer for BEAST results.** A BEAST analysis on the clock page opens its summary tree in PearTree (Andrew Rambaut, MIT) inside the app, with date, lineage, clade and country on the tips (colour by any of them; the time axis is calibrated from the tip dates). PearTree runs in the page and sends nothing anywhere. Its code is not part of this repository: the analysis page offers a one-time download of the pinned versions of PearTree and its `pearcore` library (no licence file in its repository) into the data folder, about 4 MB.
- **BEAST summary trees.** The clock page lists every BEAST analysis with a summary tree (NEXUS, made with TreeAnnotator on first use: HIPSTR by default, node heights as medians, the first 10% of the trees dropped, posterior and 95% HPD on the nodes) and a tip table (date, lineage, clade, country) to join onto the tips in a tree viewer such as PearTree or FigTree (`/api/clock/<id>/beast/tree?tag=...`). The tree holds private genome ids when the analysis used them: keep the file out of public places.
- **Pathoplexus-only records are collected too.** Records that Pathoplexus has but NCBI does not (deposited at Pathoplexus without an INSDC accession, or INSDC records NCBI has not mirrored yet) now join the check as new genomes, keyed by their INSDC accession or, without one, their Pathoplexus accession (`PP_...`). Pathoplexus is the first source for their fields; it also supplies the length, and the status (Complete from 95% of the reference length) because NCBI is not there to state them. Sequences come from Pathoplexus (LAPIS) when NCBI does not serve them, for the sample check, the apply step and "Get FASTA". The below-coverage rule applies to them as to NCBI records. NCBI stays the source of the INSDC version of its own records (Pathoplexus keeps the version it ingested, and a download by that version fails after NCBI revises the record).
- **BEAST sensitivity options**: `partition: apobec_only` / `other_only` run a plain model on the APOBEC3-context sites or on all the other sites alone, and `mask_columns` leaves chosen alignment columns out (for example sites that mutated again and again), both for checking what carries the dating information.
- **BEAST: a monophyly indicator for the groups whose stem age is logged.** The summary lists, per group, the share of the posterior samples in which the group is a clade (`monophyly`), so a country's stem age can be read together with how often its genomes form one clade. Used by the country-stratified A.4.1 analysis.
- **BEAST: genomes with only a month for a date can be used at the middle of the month** (`month_dates` in the BEAST settings; the clock run already treats them as month ranges and gives the middle as their date). The usual convention, no new BEAST feature needed; the error is at most half a month, about half a change at the rate of the mpox lineages studied here. Year-only dates are still left out. `dates.tsv` of the package says which tips are month-only. Without the option nothing changes (day dates only).
- **BEAST: a partitioned model for the APOBEC3 question** (`partition: apobec` in the BEAST settings). The alignment is split into the sites whose consensus context is TC (the C) or GA (the G) - where the host's APOBEC3 enzymes make C>T and G>A - and all other sites; each part has its own HKY + gamma and a relative rate, with the mean over the sites kept at 1 so the clock rate stays the genome-wide rate. The result lists the rate at APOBEC3-context sites, at the other sites and their ratio (clock rate x relative rate, per sample). Not available with marginal-likelihood estimation. A 20-tip, 20,000-state check ran through BEAST; no real run has been made yet.
- **"Our genomes": ties among the nearest genomes are shown.** For each genome the page says how many genomes are equally near (and from which countries and since when); the order inside a tie is only the date order, so it says nothing.
- **A Nextstrain build with the Ib lineage `clades.tsv` gets its labels put right** (`cladedefs.fix_auspice`, called by `nextstrain.run` when a dataset's `clades` file holds the sh2023 lineages). The workflow's own `clades_renaming.py` reads every name it does not know as an hMPXV-1 (sh2017, clade IIb) lineage, so the clade labels are corrected, a `lineage` attribute and colouring are added and the original is kept as `*.orig.json`. Upstream, `clades_renaming.py` needs to know the Ib lineages before such a file can be used without this step.
- **A Nextstrain `clades.tsv` for the lineages of clade Ib** (`cladedefs.py`, `/api/analyses/<run>/clades_tsv`, `?download=1` for the file, `?validate=1` for the replay). Nextstrain's clade I build labels only clade I, Ia, sh2024 and Ib (one site), so the Ib lineages (sh2023: A, A.1 ... A.4.1, A.5) do not appear on its trees. The file keeps the build's own rows and adds one `clade` row per lineage (parent = its parent lineage) with the sites that introduced it, moved from NC_063383.1 to the build's reference KJ642613.1 by a liftover. `validate` replays augur's rule on a run's SNV calls and compares it with the lineages of the genome table (sites in the inverted terminal repeat cannot be tested by it, because the mutation table leaves that region out).
- **Clock page: the molecular clock by mutation class** (`clockclass.py`). The root-to-tip regression of the dataset's Nextstrain tree is done once for APOBEC3-type changes (TC>TT, GA>AA) and once for the others, and per lineage: slope (changes per year per genome, 95%), R^2, where the line meets zero, mean changes per tip, with a scatter.
- **"Our genomes" page** (*Statistics* tab): one country's genomes (default South Korea, or only the private ones) against the rest of a run. Per genome the mutation count and APOBEC3-type share; the mutations all of them share; every mutation the group carries, classed by how often the others - and the others of the same lineage - carry it (carried by no other genome / rare below 2% / rare within the lineage / common = the lineage's own markers), with the four callers' agreement and the independent origins on the tree for the distinct ones; markers the group lacks; and each genome's nearest genomes by differing mutations. No test is done for groups under ten genomes.
- **Adaptive candidates: inseparable mutations flagged (E9, the part the data allows).** Linked pairs (`co_travel`) now carry `identical` when two mutations sit on exactly the same genomes; the panel says how many such pairs there are, because no analysis of these genomes can tell which of them acts. A regularised regression to split looser links was not built: the Ib data have too few lineages for it to identify anything (see docs/ADAPTIVE.md).
- **Four-model comparison for BEAST** (clock page, below BETS). The four combinations of clock (strict, relaxed) and tree prior (constant, exponential) are all run with the real dates and ranked by marginal likelihood (GSS, with PS/SS beside it); each model's log Bayes factor against the best is shown with the spread of the three estimators (over 2 is flagged). Settings come from the BETS card; the analyses run side by side as separate BEAST processes in `bets/models/`, recorded as an `analysis_run` (tool `bets`, note `clock:<id>:models`). BETS itself is unchanged. A real run has not been made yet: it takes hours.
- **Adaptive candidates: independent-evidence count, HyPhy input export, predecessor comparison.** The panel says "N candidates = M independent pieces of evidence" (linked groups count once). *HyPhy input* downloads a zip with a codon alignment per candidate gene and the tree (`hyphyexport.py`; public genomes only; the tests are run outside the app). docs/ADAPTIVE.md section 8 compares with MpoxRadar and PyR0 (read in full text); VIRUS-MVP could not be read.
- **Adaptive candidates: neutral baseline, country-adjusted rise, evidence ticks, recovery test.** (E8) Recurrence is compared with the independent-origin counts of synonymous / non-coding mutations of the same class (APOBEC3-type, transition, transversion) with a Poisson or negative-binomial tail and BH q (`origins.neutral_baseline`). (E5) Each mutation gets a logistic slope over months with a per-country intercept (`trend.py`). The candidate table now has tick columns for persistence, recurrence, above-neutral, spread, protein change, rise and adjusted rise, with the score only as a sort aid. `./test.sh verify` gains a simulated recovery test (planted five-origin mutations recovered, null false positives about 0). Not done: regularised separation of linked mutations (E9), HyPhy export (E10), the predecessor comparison table; see docs/ADAPTIVE.md.
- **Adaptive candidates: independent origins counted on the Nextstrain tree** (`origins.py`, evidence E7 of docs/ADAPTIVE.md). Recurrence is now the number of tree branches (with at least two descendant genomes) that carry the same mutation, replacing the lineage-name approximation whenever the dataset has a tree on the run's reference; single-tip origins are counted apart, mutations absent from every branch are marked as older than the tree. New class *recurrent* (arose independently at least twice). The page shows how many mutations recur and which of them are persistent, protein-changing and not APOBEC3-type.
- **Design notes for identifying adaptive mutations** ([docs/ADAPTIVE.md](docs/ADAPTIVE.md)): evidence types E1-E10 against what is implemented, the approaches found in the literature (abstract level), the proposed methods (independent origins on the tree, a neutral baseline from synonymous / non-coding mutations, country-stratified growth, linked-mutation handling, HyPhy export), a validation plan and a prioritised to-do list.
- **Adaptive candidates as a flow diagram and a mind map.** The candidate panel has three views: the table, a *network (flow diagram)* - x = month first observed, one lane per functional category, circle size = carrying genomes, lines between mutations that sit on (nearly) the same genomes (Jaccard >= 0.6, arrow from the earlier to the later), with the linked groups listed below because mutations that always travel together are one piece of evidence, not several - and a radial *mind map* (functional category > gene > mutation). Click a node for its spread timeline, right-click for the usual menu.
- **Mutation picture: functional-category, effect and adaptation highlights, and a list of candidate adaptive mutations.** The highlight legend gains the gene functional categories of the paper's Supplementary Table 1 (host modulation, genome replication/transcription, surface protein, assembly/budding, unknown), the protein effect, and the *adaptation* classes. *Adaptive candidates* are an exploratory ranking of mutations the virus seems to keep: seen in at least three months and still in the last six, carried by genomes of at least two lineages that they do not define (+2, three or more +1), in three or more countries (+1), changing the protein (+1), with the share among the sampled genomes holding up (+1) and rising from rare early to common recently (+2). Mutations carried by nearly every genome (ancestral to the set) and lineage-defining mutations are set apart, APOBEC3-type changes are kept in their own class (a host edit, no evidence of selection). The list shows the evidence for each; it is not a test of selection (hitchhiking on a successful branch and uneven sampling score high too).

### Fixed
- Adding a watch for a virus that is already watched no longer ends in a database error: the page says which watch it is and opens it.
- **`./test.sh verify`** (`scripts/verify_pipeline.py`): checks the *results* of the pipelines on the real data, read-only - the curated data's integrity; the vocabulary is idempotent; the QC headline follows the priority; private genomes are in nothing public; the Nextstrain tree's tips are run members and their clades equal the curated ones; Squirrel's alignment + QC exclusions = the members and every aligned genome is a tip of its tree; every mutation's reference base equals the reference at that position, gene / amino-acid change recomputed independently, summary count equals rows; the mutation profile against Nextclade's alignment of the same genomes (60 random genomes: precision 100%, recall 97.2%); snippy / lofreq agree with the run on 93.2% of calls; the Snakemake flow equals the direct implementation; lineage-defining mutations are carried by their lineage (99.9%); the timeline of chosen mutations equals the carriers in the table; the known hotspot (OPG175) is found; and a planted-substitution test with a known answer. Result on the clade Ib data: 29 pass, 2 warnings, 0 failures.
- **Mutation Gantt chart** (mutation picture, view *시간 간트*; `genomecurator/mutgantt.py`, `GET /api/analyses/<id>/mutation_gantt`): one row per mutation, time on the x axis in ISO weeks or months, a cell coloured by how many carrying genomes were collected in that period (pink rows are APOBEC3-type), the bar from the first to the last observation, a diamond at the first observation, and the rows **ordered by when each mutation was first observed** (earliest on top; or by position, or by number of carriers). The picture's filters apply (lineage, clade, gene or region, APOBEC3 only, drop what almost every genome carries - 90% by default in this view), plus a minimum number of carriers and a row limit; right-click a mutation for the heat map / spread timeline menu. A genome whose date has only a month is in the monthly view and not on a week; a genome without a date is left out (the count is shown). *First observed* is the earliest collection date in the sample, not when the mutation arose, and a month-only date counts as the start of its month - the page says so.
- **BETS - is there a temporal signal?** (clock page, `genomecurator/beastprep.py`, `POST /api/clock/<id>/bets/run`): before a BEAST tMRCA is believed, two analyses of the same model on the same subsample run side by side - one with the real sampling dates, one with every genome given the same date (the isochronous model) - each followed by path-sampling and stepping-stone estimation of the marginal likelihood (`marginalLikelihoodEstimator`, BEAST 10.5 accepts the XML the app writes). The log Bayes factor (dates - no dates) is read on Kass & Raftery's scale: 5 or more is strong support for a temporal signal, -1 to 1 means the dates do not help, below -1 favours no dates; when the dates do not win, the BEAST tMRCA is set by the prior, not by the dates. Proper priors only (the clock rate and population size get log-normal priors), since a Bayes factor needs them. Defaults follow the recommendation for a reliable estimate (50 path steps of 250,000 states after a 1,000,000-state initial chain); PS and SS are both reported and a gap above 2 between them is flagged. **A short test (10 steps of 10,000) gave a log BF of 700-950 with PS and SS 250 apart, i.e. a short run is meaningless - the page says so.** **Generalized stepping-stone sampling (GSS)** is implemented too (default *GSS + PS/SS*): an ordinary chain of each model first, then a working prior (log-normal for the positive parameters, normal for the growth rate, a matching coalescent for the tree) built from that chain's posterior, then the path - the XML follows what BEAUti writes (element names read from the BEAST 10.5 jar, validated by running it). It needs fixed base frequencies (the alignment's own: a simplex has no working prior) and a start inside the working prior (the chain starts from the middle of the earlier posterior; started outside, BEAST refuses it). On a simulated alignment (12 genomes, 400 sites, 100 steps of 50,000) GSS -1223.4, stepping-stone -1222.7 and path sampling -1222.7 agree (`./test.sh verify` runs that check); with 10 steps of 10,000 they differ by up to 4, which the page also flags.
- **Molecular clock and tMRCA** (`genomecurator/clock.py`, page `/clock/<id>`, dataset panel *분자시계·tMRCA*, pipeline step `clock`): **stage 1** is TempEst's root-to-tip regression (TempEst itself is a Java GUI; TreeTime's `clock` does the same least-squares regression, re-roots for the best fit and drops the tips that do not fit): substitution rate, R^2, root date, outlier tips, an interactive scatter. **Stage 2** is a time-scaled tree (TreeTime, branch lengths kept as they are) with a date and 90% interval for every node; the tMRCA of the root and of every clade / lineage that has enough genomes (with a flag when the group is not monophyletic). Tree: Squirrel's ML tree (default) or the Nextstrain tree; dates: curated collection dates (a day as it is, a month as its range, nothing less precise unless asked); every run is recorded in `analysis_run` and reused when the tree, dates and settings are unchanged. Next to the numbers the page lists what limits them (weak clock, a short sampling period, a wide interval, outliers, month-only dates, the root assumption). The page says when the clock is weak and a root date is an extrapolation.
- **BEAST** (`genomecurator/beastprep.py`, on the clock page): a package from a clock run - a subsample of up to 600 genomes that keeps the whole sampling period and every lineage (day-precision dates, no clock outliers), the Squirrel alignment of those genomes, tip dates and a BEAST 1.10-style XML (HKY + gamma; strict or uncorrelated log-normal relaxed clock; constant-size or exponential coalescent; tMRCA statistics for the root and the lineages) - and a background run of BEAST 10 with the posterior read back (median / mean / 95% HPD of each tMRCA and the clock rate, **ESS** with a warning below 200) beside TreeTime's numbers. Environment `gc-beast` (`variantcall/beast.yml`: BEAST 10 and the BEAGLE library BEAST 10 needs to evaluate the likelihood; an existing `beast` environment is used only if it has BEAGLE too). Short chains are far too short to use: the page says so.
- **`./test.sh verify` and `check` cover them**: invariants of a clock run (the root date inside its own interval, every tMRCA earlier than the earliest sample, positive rates), a **planted-clock test** (a tree simulated with a known rate and root date: TreeTime recovers the rate within 5% and the root within a year), and a BEAST smoke test (the app's XML for random sequences runs in BEAST/BEAGLE).
- **QC priority: Squirrel > Nextclade > CheckV** (then the built-in sequence statistics): the headline QC status of a genome - the *QC* column of the genome table, the dataset rule *QC excluded*, the export filter - follows the verdict of the highest-priority tool that has a real result; a tool that errored has no verdict. The other tools' verdicts stay visible (the worst of all is kept as `qc_worst`). Before, the headline was the worst of all tools.
- **One button for all analyses** (dataset page, *한 번에 분석*, `POST /api/datasets/<id>/analyze_all`, `genomecurator/pipeline.py`): QC -> Squirrel -> mutation profile -> variant calls (snippy + lofreq) -> Nextstrain, the steps you tick, one after the other as one background job. Each step is the same function as its own button, so an unchanged step (same members, content, settings and tool version) is reused; a failing step does not stop the others (the variant calls are skipped when their mutation profile failed); Nextstrain is last because it takes longest. For a virus whose analyses are not built (see the status badges) only QC runs, and the result says so.
- **CheckV database**: `checkv download_database` ends with a DIAMOND index built by the environment's own `diamond`; run outside the activated environment that last step fails although the 1.5 GB were downloaded (the app now says to run it with `conda run -n gc-checkv`). Verified on real genomes: six clade Ib genomes in 15 s (five High-quality, one Medium-quality at 90% completeness).
- **Make a dataset from the genome table, analyse it right there**: the genome table has a *데이터셋 만들기* button (the selected genomes, or the rows the filters show; private ones too) that creates a dataset holding exactly those genomes (new rule `only_manual`, shown as *고른 유전체만*) and opens its page. Results from identical input are reused instead of recomputed.

- **Coldspots** (*유행 분석*, section 5): the opposite of the hotspot search - genes and 10 kb windows with significantly **fewer** independent mutation events than expected. ### Fixed
- **Gene hotspots were an artefact of inheritance**: the outbreak analysis ranked genes by mutations summed over genomes, which counts one ancestral mutation once per descendant, so the top genes were those carrying clade-defining mutations (62 "hotspots"; one gene's 342 "events" were a single mutation inherited by 342 genomes). Hotspots are now **independent mutation events on the tree's branches** per gene against the genome-wide rate (Poisson, Bonferroni over genes): in the Clade Ib dataset 826 events are spread almost evenly (4.5 / kb) and **one gene, OPG175 (virion core), is a significant hotspot** (10 events, 26 / kb against 1.7 expected). Recurrent mutations (the same change on three or more branches) are listed; the summed count stays only as a reference column.
- **Validity review of the analyses on real data** (`docs/VALIDITY.md`) and what it changed: (1) the **ITR ends (6,500 bp each) are masked by default** in the mutation profile (`mask_itr`, `itr_bp`; also when old runs are read) - a quarter of the "new mutation" candidates were in the ITRs; (2) a genome's **N / ambiguity share** is measured (`samples.tsv`) and count-based analyses take an **N-share limit** (default 5 %); (3) carrying a lineage-defining SNP is **three-valued** (carries / lacks / unknown for N, deletion or uncovered), which showed that the SNP calls and the lineage definitions agree (all-sites-known genomes carry all defining SNPs of their lineage, 94-100 %) - the earlier 74.7 % was N; (4) the APOBEC3 accumulation also gives the **within-lineage trend** (without the N limit it vanishes - phylogenetic depth and N undercounting had inflated it); (5) the APOBEC3 transmission test is repeated with distinct-only / homoplasy-free variants (same conclusion: ~80 % of inherited mutations are APOBEC3-type, p about 0.001-0.002).
- **An old analysis is no longer presented as current for data that changed under the same ids**: runs were compared with the dataset by the member ids only, so a new sequence version, a corrected curated value, new QC or a new version of a private genome still read as *same members* and an identical earlier run was reused. Every run now also stores a content fingerprint (per member the exported metadata row and the sequence md5; private members with their version); a change shows as *same ids, but sequence version / values / QC changed*, the run is not reused, and runs made before the fingerprint existed say that their content cannot be compared.
- **Cross-site writes are refused for every route**: ten POST routes that predate the per-route origin check (approve / apply a changeset, `deploy`, `watch/.../check`, sequence uploads ...) accepted a request from a page of another site opened in the same browser. A global guard now refuses any POST / PUT / PATCH / DELETE whose `Origin` is another site (or `null`, or `Sec-Fetch-Site: cross-site`); same-origin use and reading are unaffected.
- **Backup now keeps your dataset decisions**: the general backup left out saved datasets, *exclude from dataset* marks and the export history, so a restore lost them. They are included; anything that names a private genome (private ids in manual lists, private exclusion marks, the `include private` flag, Pathoplexus packages) stays out unless `--with-private`.
- Concurrent database connections could fail with `view v_genome_analysis already exists`; the analysis view is now rebuilt only when its definition changed, in one transaction.

## [0.2.0] - 2026-10-17

Makes the quality of a genome and the disagreement between sources something you can *act on*: a Near complete class, a way to choose between the
sources' values with a suggestion, and two ways to read the schema check. The tool is now explicitly for viruses only.

### Changed
- A host that differs only by a common name in parentheses (`Sus scrofa` vs `Sus scrofa (pig)`) is now a *cosmetic* difference, not a conflict.
- **Scope and name.** The tool is for **viruses only** (NCBI Virus, BV-BRC, Pathoplexus); bacteria will be a separate project because genomes there are
  assemblies made of many contigs and are megabases long. To stop "genome" from being read as *human genome*, the displayed name is now
  **Virus Genome Metadata Curator** (**Virus Genome Curator** in the page header, titles and messages). The repository, the Python package `genomecurator`, the
  command line, the data folder, environment variables and the backup format identifier are **unchanged**, so nothing needs migrating.

### Added
- **Choosing between the sources' values** in the review screen. Click an item and the side panel lists every field the sources disagree on, with each source's value and whether
  it is only written differently or really different. A **suggestion (★)** is pre-selected with its reason and confidence: an impossible date is left out; length/version follow NCBI
  (the sequence is downloaded from NCBI and its length verified); values that are the same fact in different words go to the best-written one (most specific date, scientific
  host name, standard country name) = *high*; a value most sources agree on = *medium*; otherwise the source priority decides and the person is told to look = *low*.
  Pick a value or type your own and save: it is applied to the item at once and **kept by every later check** (the chosen source's current value is used; a typed value stays as typed;
  *manual* is shown as the source). Choices can be undone per field. **Auto-pick** in the toolbar selects the suggestions of *medium* confidence or better in one go and leaves the *low* ones
  to the person. Choices are stored in the new table `field_choice` and are part of backups; fields a person has decided no longer count as open disagreements.
- **Near complete** genomes. NCBI only distinguishes Complete from Partial, but most of the "Partial" genomes are missing just a few hundred bases at the ends. A new
  *Completeness* class sits between them: **Complete** (NCBI says Complete; trusted, so a lineage that is legitimately shorter than the reference is not demoted),
  **Near complete** (not Complete, length at least **90%** of the reference genome) and **Partial** (below that, or no reference). The reference of a virus is its longest
  RefSeq genome among the collected records. The threshold is `GC_NEAR_COMPLETE_PCT` (default 90, the CheckV high-quality cut-off; on real data it sits in the valley of the length
  distribution: for mpox only 33 of 13,462 genomes lie between 50% and 90%). Shown as a column, a filter and dashboard KPIs, on the public page, and in the analysis view
  (`completeness`, `ref_coverage_pct`, `ref_length`), which applies the same rule in SQL. On the mpox data 7,583 of the 8,223 NCBI-Partial genomes are Near complete.
- **Simple view** on the **Schema** tab (the default; a tab switches to the detailed board below): one table with the local `genome` columns as rows and
  NCBI / BV-BRC / Pathoplexus as columns, each cell naming the source field that fills the column, coloured by status. Columns that need attention are
  listed on top with the source field to look at; columns are grouped (identity, taxonomy, genome, sample, dates, external IDs). The choice of view is remembered.
- **Table structure board** (the detailed view) on the **Schema** tab: the fields of NCBI (nested objects kept as groups), BV-BRC and Pathoplexus on the left, the columns of
  the local `genome` table on the right, joined by lines that show which source field fills which column. The links are *measured*, not declared:
  the real adapters are run on a row holding one field at a time, and the columns that change are the ones it feeds (so fallbacks such as
  "A, else B" and one field feeding two columns are found too). Vanished fields turn red, the columns they fed turn orange (a warning when
  another source still fills the column, an error when none does), new fields blue; hovering highlights a connection, clicking shows the source
  fields behind a column in priority order, with type, fill rate and an example. A source whose response shape changed gets a red banner.

### Changed
- The Schema tab now starts with the full check and its board; the daily per-virus check moved below it.
- Vanished-field detection also considers the fields the code read at the last good baseline. What the code reads depends on the data
  (an absent `host` object hides `host.organism_name`), so a vanished parent used to hide its children.

### Fixed
- The schema check reported a fill rate above 100% for lists of objects (such as the lineage of an NCBI record) because each list element was counted;
  a record now counts once.

### Data & compatibility
- Schema version stays **1**. The only database change is the new table `field_choice` (your choices between source values), created automatically the first time
  0.2.0 opens a database; nothing existing is altered. A 0.1.0 backup restores into 0.2.0, and 0.2.0 backups include `field_choice`.
- The analysis view `v_genome_analysis` gained the columns `completeness`, `ref_coverage_pct` and `ref_length`. In Superset run `scripts/superset.sh bootstrap` once
  to refresh the dataset and see them. The view reads the Near complete threshold from `app_meta.near_complete_pct`, which the app keeps in step with `GC_NEAR_COMPLETE_PCT`.
- New environment variable: `GC_NEAR_COMPLETE_PCT` (default 90).
- Genomes that NCBI marks *Partial* may now read *Near complete*; nothing is rewritten, the class is computed when shown. The NCBI status is still available as its own column.

## [0.1.0] - 2026-10-17

First release. It collects virus genomes from three public sources, lets a person review and approve every change, and checks
that the sources agree with each other, with the sequences, and with the code's own expectations.

### Added

**Collecting and merging**
- Watchlist: register a virus by name. The name is first looked up in ICTV, NCBI Virus, BV-BRC and Pathoplexus; names that are not
  viruses are refused with candidate suggestions. Watches can be edited and deleted (typed confirmation and an impact preview).
  A strain or sub-species is widened to its species so records tagged at the species node are not missed.
- Three sources. **NCBI Virus** (Datasets v2) defines which accessions exist; **BV-BRC** and **Pathoplexus** enrich them.
  Pathoplexus organisms are discovered from the site itself and matched by NCBI taxon (including descendants); organism-specific
  fields (clade, lineage, serotype, outbreak, genotype, subtype) are read automatically.
- Field priority is Pathoplexus > NCBI Virus > BV-BRC, and the source that supplied each field is recorded (`field_provenance`).
- Columns include SRA, BioProject, BioSample, sequencing platform and assembly method, with NCBI links.
- Every web request is spaced at least 300 ms apart and retried with exponential backoff (up to 3 times).

**Review and apply (changesets)**
- `check` never changes local data. It produces a *changeset* of new / changed / removed records (a changed record means a metadata
  change or a higher GenBank `.version`). Nothing becomes local data until a person approves it; rejected items do not come back
  when their content is unchanged.
- Approve / Reject / Hold in a spreadsheet-style review grid, including selections above 1,000 rows and a one-click approve + apply.
- A dry-run precedes every apply: free disk space, links, and sample sequences. Apply is atomic: files are backed up first and
  everything is rolled back on an exception; individual failed accessions are skipped and reported; interrupted downloads resume from
  staged files.
- Metadata-first apply (FASTA can be fetched later with *Get FASTA*), and no FASTA download for metadata-only changes.
- Changesets can be deleted (impact preview, confirmation). The review screens are written in plain language with step-by-step guidance.

**Data integrity**
- Cross-source reconciliation at every check: each field is classified as *match*, *cosmetic* (same fact written differently, e.g.
  `USA: CA` vs `USA, CA`, `2022-07` vs `2022-07-11`) or *conflict*, plus coverage (which source has which accession). Shown on the
  **Integrity** tab and as a column, filter and warnings during review.
- Sequence-body verification: sequence bodies (header and whitespace removed, upper-cased, SHA-256) from NCBI, BV-BRC and Pathoplexus
  are compared for accessions whose length, version or hash disagree, with NCBI as the reference. A dry-run plan comes first (light
  length queries decide most cases without downloading), results are resumable, and a source that holds NCBI's exact sequence resolves
  that pair's length/version conflict.
- `verify`: FASTA length and md5 against the records, dates, orphan rows, and more.
- A source that fails to respond now stops the check instead of being skipped, because merging without it could blank curated fields.

**Source schema monitoring**
- Schema dry-run (`schema-check`, **Schema** tab): the fields the adapters really read are measured by running them over live samples,
  then compared with the previous baseline to find vanished, retyped and new fields and changed response shapes, and the local database
  is checked against what the code expects. The report says whether the source code needs an update and where.
- A baseline that shows problems is not replaced until a person accepts the new state.
- A daily per-virus check (3 records per source per virus, 03:00) with a badge on the **Schema** tab when something needs attention.

**Web interface**
- Spreadsheet-style grids with facet filters, sorting, column picker, TSV export and maximize; a detail panel with per-value source
  badges and Pathoplexus variant details, whose width can be dragged; dashboard charts; one consistent layout.
- A progress modal with a large bar and a server-kept job log that survives page reloads; a history page with the server log viewer.

**Analysis and publishing**
- Apache Superset integration: a read-only flat view (`v_genome_analysis`), `scripts/superset.sh`, and 10 charts plus a dashboard
  created through its API.
- A read-only public page (`docs/index.html`, also served locally at `/public`) and a one-click publish to GitHub Pages.

**Operation**
- Windows, macOS and Linux: OS-independent data folder, UTF-8 / LF files, portable relative FASTA paths, safe folder names, and
  launch scripts that prefer a conda/mamba environment (`environment.yml`, plus `superset/environment.yml`). CI runs a three-OS matrix.
- Portable backup and restore (`backup` / `restore`): curated data, decisions and FASTA; refuses a backup from a newer database layout.
- Structured logging: a rotating log file with job / watch / changeset context, every HTTP attempt (secrets masked), and failures kept
  in the audit log even when the failed work is rolled back.
- Versioning: the version has one source (`genomecurator.__version__`); `genomecurator --version`, the page footer and `/api/version`
  show it; the database, every changeset and every backup record which version produced them.

**Documentation**
- A rewritten README with demo GIFs that a script records from the real application (`scripts/demo/`), this changelog, the release process
  ([docs/RELEASING.md](docs/RELEASING.md)) and the list of libraries used ([docs/DEPENDENCIES.md](docs/DEPENDENCIES.md), generated from the installed packages).

### Dependencies
- Python **3.10 or newer** (tested on 3.10 and 3.12; the conda environment uses 3.12).
- Runtime: `fastapi>=0.110`, `uvicorn>=0.29`, `jinja2>=3.1`, `httpx>=0.27`, `apscheduler>=3.10,<4`, `python-multipart>=0.0.9`.
- Optional: `pytest>=8` (tests); `pillow>=10` and `websocket-client>=1.6` (recording the README GIFs, plus Google Chrome);
  Apache Superset `6.1.0` with `rich`, `cachetools` and `flask-caching<2.4` (analysis, separate environment).
- In the browser: Chart.js 4.4.1 from the jsDelivr CDN (charts need internet).
- Data come from NCBI Datasets, BV-BRC, Pathoplexus (LAPIS) and, for name checks, ICTV through EBI OLS4.

### Data & compatibility
- Database layout (schema version **1**): all changes so far are additive migrations applied automatically when the app opens a
  database, so a database from an earlier development build upgrades in place. The first time 0.1.0 opens a database it records
  itself in the audit log (`version`) and `app_meta`.
- Backups made by this version carry `app_version` and `db_schema_version` in `manifest.json`.

### Known limitations
- The daily schema check samples the *first* records NCBI and Pathoplexus return (older records), so a change that only appears on
  new records can be noticed late; run the full check from the **Schema** tab now and then. BV-BRC is sampled newest-first.
- Identical sequence bodies prove two records are the same entity; they do not prove that host, date or other metadata is correct.
- The scheduler (daily checks) runs only while the server is running.
